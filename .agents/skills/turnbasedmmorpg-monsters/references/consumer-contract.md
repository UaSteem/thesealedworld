# Consumer contract

For a caller migration, start with the [implementation handoff and separate tasks](../../../../docs/ru/backend/features/monsters/consumer_migration.md). It distinguishes accepted catalog behavior from the unfinished live GS, instance delivery and Rift/Exploration integration. Presence in `monsters.public` alone does not make a retired service usable.

For seed ownership and operational logging, read [Seeds and selection logs](../../../../docs/ru/backend/features/monsters/seeds_and_logging.md). Consumers derive world/region/encounter seeds or persist independent rift-instance seeds; Monsters only consumes the ready seed. Keep order/results persistent in their owning domain, not in operational logs. World/Rift wiring remains unimplemented.

Read [the maintained encounter contract](../../../../docs/ru/backend/features/monsters/squad_contract.md) and its linked JSON examples before integrating a caller. Use public exports from `src.backend.features.monsters.public`; do not import internal composition profiles into callers.

The external `MonsterEncounterOrderDTO` contains `encounter_type` (ordinary/patrol/guard/leader), `location_tier`, exactly one entry in `family_ids`, required integer `seed`, `difficulty` (easy/normal/hard, default normal), `party_mode` (solo/group, default solo), optional finite nonnegative `player_gear_score`, and optional typed `profile_override`. Tag filters remain internal; external tag fields are rejected even when empty. Normal callers use builtin profiles; tests/events may supply a complete override profile, replacing builtin rules without merging.

Group mode returns `group_profile_unavailable` before catalog search; never substitute solo. Builtin profiles use party mode -> encounter type -> difficulty, shared across organizations. Each profile defines independent minion and senior (veteran/elite/boss) budgets, allowed ranks and rank minimums/maximums. Ordinary encounters allow only minions. Patrol requires a veteran, guard an elite, leader a boss. Seniors are selected first; remaining slots are filled with minions under their own budget. Only the overall squad has a minimum size; minions have no mandatory minimum; no points transfer between pools. Catalog members carry explicit positive `assembly_cost`, independent of GS and combat stats. Builtin minion pools require player GS: effective points are floor(min(base_points * player_GS / reference_GS_of_location_tier, base_points + gs_bonus_max)). There is no second stepped bonus on minions or hidden minimum budget. Senior pools keep independent capped step bonuses. External fixed test profiles may omit GS. Measured reference GS and provisional tiers are exposed by contract metadata; do not duplicate these tables in callers. Monster GS is not used for selection. High player GS never changes tier/allowed ranks/difficulty or bypasses the overall eight-member ceiling. Starter prices and budgets are provisional, not calibrated combat balance. Read the contract for current data and arithmetic.

`MonsterEncounterPreparationService.prepare(order)` resolves admission, ready candidates and composition configurations. `prepared` does not mean squad selected, all configurations feasible or combat spawn available. Handle validation errors separately from `rejected` with typed reasons. Never silently relax filters or invoke retired runtime.

`MonsterEncounterSelectionService.select(order)` verifies feasible rank-requirement/clan combinations, then selects a concrete squad reproducibly by seed. Result contains status, preparation, selection or null, rejection reasons, attempts, profile source/ID, variant ID and separate minions/seniors base/bonus/effective/spent/remaining diagnostics, plus aggregate accounting sums. One order targets one family, one selected squad belongs to one clan. Selected members reference catalog definitions and admitted tiers; they are not runtime actors. Never accept missing mandatory ranks or silently raise the budget on rejection.

Studio checks selection through the same API contract at `/admin/content-ops/monster-encounter`; protected read-only endpoints are documented in the contract. World and Rift are not connected at this stage. Before integrating them, verify the current result contract and whether instance delivery has been implemented.


Cached API selection uses CachedMonsterEncounterSelectionService through dependency wiring. Redis pools are created lazily on the first request and expire after 86400 seconds; reads do not extend TTL. Cache identity includes effective integer budgets, complete profile constraints, family/location tier/mode/type/difficulty and the process source-semantic revision; seed and raw GS are excluded. Hits rebind the current order and GS diagnostics. Candidate readiness and compact candidate-index variants are cached together. Independent Redis leases use token-fenced renewal/publish/release; same-key callers wait rather than duplicate builds. CPU work is bounded and off the event loop. Redis failure or bounded wait exhaustion returns HTTP503 monster_pool_cache_unavailable; there is no silent uncached fallback. X-Monster-Pool-Cache reports miss/hit/wait. App restart preserves valid Redis entries; Redis persistence itself is an infrastructure concern. Sync select remains a detached uncached domain entry point for tests/tools, not the API hot path.

`await CachedMonsterEncounterSelectionService.select(order)` returns `(result, cache_status)`; the API unwraps this into the response DTO plus header. Follow `api/dependencies.py`: reuse the app-scoped service and `redis_managers.monster_encounter_pools`, rather than creating an HTTP request to the protected admin route or a new service/limiter per encounter. A future non-HTTP consumer needs equivalent application composition-root wiring and its own typed infrastructure-error boundary. Preparation and synchronous selection are not asynchronous cached spawn APIs.
