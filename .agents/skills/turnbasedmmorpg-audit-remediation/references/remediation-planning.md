# Варианты исправления и порядок

Планируй по подтверждённой первопричине, сохраняя ссылки на все исходные audit finding ID. Для каждой задачи укажи текущий участок кода и владеющий контракт, ожидаемое поведение, локальное исправление и системный вариант **только если** локальный не удерживает правильную границу. Для вариантов сравни пользу, цену, риск регрессии и затронутые домены. Не предлагай большой рефакторинг или новую библиотеку, очередь, БД либо сервис без доказанной необходимости.

Выбери проверку результата по наблюдаемому контракту: regression test для конкретного дефекта, integration test для реальной границы API/DB/Redis/event и иной нужный контроль из [quality](../../turnbasedmmorpg-quality/SKILL.md). Отметь предполагаемые миграции данных, release/wipe риск и публикационный gate через [release](../../turnbasedmmorpg-release/SKILL.md); планирование не запускает эти действия.

Очередность строй по реальному риску и доступности, стадии поверхности, общим первопричинам, тестируемости, сложности, зависимостям и риску для соседних доменов. Покажи минимум один выполнимый порядок, а при существенном выборе — альтернативу с последствиями. Раздели независимые задачи для параллельной работы и задачи, которые должны ждать общего контракта. Не назначай исполнителей автоматически и не выбирай окончательный объём за владельца.

Для неподтверждённых находок сначала формулируй ограниченную проверку, а не реализацию гипотетического исправления. Уже исправленное или неактуальное сохраняй в учёте со ссылкой на evidence. При публичной критической угрозе сообщай владельцу сразу, отдельно от очередности обычного плана.
