# Ассеты боевого интерфейса: измерения и runtime-план

Дата: 25.10.2026. Проверялась текущая сцена `hex` на localhost:8879.
Ни один исходный ассет в рабочем стенде не заменён уменьшенным.

## Фактический бюджет

На первоначальном открытии браузер запросил **56 локальных файлов, 9,082,889 bytes
(8.66 MiB)** без HTML и HTTP-заголовков. Это размер файлов, а не измерение времени
скачивания или трафика с gzip/brotli/CDN. SVG, которые Phaser превращает в blob,
не считаются повторными сетевыми загрузками.

Для будущего переноса нужна сборка используемых зависимостей, а не копия всего стенда. Список файлов и источников находится в `../asset-manifest.json`.

| Растр | Размер | Файл, bytes | RGBA8, MiB |
| --- | --- | ---: | ---: |
| Плитка и обломки | 2048×2048 | 1 316 225 | 16 |
| Правая панель управления | 2048×2048 | 856 149 | 16 |
| Рамки игрока/монстра/босса | 2048×2048 | 2 324 988 | 16 |

Итого эти растры: **7 703 047 bytes (7.35 MiB)** файлов и **135 MiB** базовых
RGBA8-поверхностей. Старый неиспользуемый лист уже исключён из preload при разделении клиента. Дополнительно Phaser растеризует
17 SVG-иконок по 96×96: около 0.60 MiB RGBA8. Много карточек использует одну
текстуру: атлас не копируется целиком на каждого участника.

Это расчёт `width × height × 4`, **не замер VRAM или общей памяти браузера**.
Не учтены framebuffer, canvas-тексты, временные декодированные копии, драйверные
накладные расходы и возможные mipmaps. CSS-космос хранится и композится браузером,
он не находится в Phaser Texture Manager.

## Когда 1024 → 512 оправдано

Нужно сравнивать пиксели источника с **физическими** пикселями показа:
`логический размер × CSS scale × devicePixelRatio`. На базовом окне 1920
host имеет ширину 1597, radius≈92.06. Ниже — измерения на DPR 2.

| Элемент | Источник кадра | Показ, logical px | Показ, physical px | Рекомендация |
| --- | --- | --- | --- | --- |
| Плитка / обломок | 1024×1024 | 209.5×209.5 | 419×419 | 512×512 на кадр достаточно по плотности |
| Активный игрок | 836×729 | 220.9×192.7 | 442×385 | Тесный экспорт шириной 512 |
| Активный монстр | 852×772 | 220.9×200.2 | 442×400 | Тесный экспорт шириной 512 |
| Активный босс | 946×822 | 260.7×226.5 | 521×453 | Лучше ширина 640, запас при анимации |
| Ожидающий игрок / монстр | 836/852 по ширине | 173.1 по ширине | 346 по ширине | 512 с запасом |
| Круг | 1024×1024 | 828.5×828.5 | 1657×1657 | Не уменьшать; master 2K желателен для DPR 2 |
| Каркас управления | 920×350 | 552×210 | 1104×420 | Не уменьшать исходный crop |
| Плита управления | 920×286 | 552×171.6 | 1104×343 | Не уменьшать исходный crop |
| Плашка финта | 840×106 | 270×34.1 | 540×68 | Экспорт шириной 640 |
| Кнопка атаки | 840×116 | 270×37.3 | 540×75 | Экспорт шириной 640 |
| Квадратный слот | 640×640 | до 54×54 | до 108×108 | 128–192 на кадр |
| Инспектор | 553×975 | 230×470 | 460×940 | Сохранить текущий тесный crop |
| Плашка раздела | 980×125 | 190×27 | 380×54 | Экспорт шириной 512 |
| Медальон намерения | ≈302×304 | 32×32 | 64×64 | 96–128 на кадр |

«Кадр 1024→512» не означает «весь лист 2048→512». Для листа 2×2
переход **2048→1024** даёт четыре кадра по 512 и снижает RGBA-память **16→4 MiB**.
Переход листа 2048→512 оставит всего 256 на исходную ячейку — это другая плотность.

При простом уменьшении листа рамок вдвое player crop станет шириной418,
monster426, boss473: активные рамки уже будут увеличиваться на DPR 2.
Поэтому лучше экспортировать кадры отдельно и затем перепаковать атлас.

Оценка 512 здесь — обоснование по геометрии, **не визуальная приёмка уменьшенных
версий**. Перед подключением нужно сравнить золотые линии, альфа-края, руны
и каналы ресурсов на реальных размерах. В этом снимке downscale не применён.

## Не загружать художественные планшетки как окончательные runtime-пакеты

Один огромный лист для всей игры не нужен: он заставляет загружать невидимые
биомы и интерфейсы. Но небольшие атласы по совместному использованию полезны:
меньше запросов и переключений текстур. Делить каждый элемент в отдельный файл
тоже необязательно.

Предлагаемые группы:

1. **shell-common:** шрифты, общие иконки и статус. Живёт всю игровую сессию.
2. **battle-terrain:** четыре кадра плитки/обломков по512, атлас1024² — 4 MiB.
3. **battle-frames:** тесные player/monster512 и boss640, metadata origin и
   ресурсных каналов. Размер упакованного атласа определяет реальная укладка.
4. **battle-controls:** используемые каркас, плита, плашки и слот; без пустот
   исходного планшета. Сохранять нужную плотность крупных частей.
5. **battle-inspector:** только чистая панель, плашка и три медальона. Панель
   с фиксированными перегородками, скошенный корпус и старый желоб сейчас не нужны.
6. **battle-circle:** отдельно1024, затем отдельный 2K tier при наличии master.
7. **battle-background:** один выбранный фон нужной плотности; не все биомы сразу.
8. **portraits:** отдельно по видимым участникам; заранее только ближайшие
   кандидаты очереди, а не все1000 участников большого боя.

Оригинальные PNG остаются masters. Для повторяемой сборки нужны source rect,
целевой размер, padding/extrusion и metadata. Существующие ручные `crop` и
`resourceProfiles` нельзя оставить прежними после уменьшения PNG: пересчитать
координаты либо хранить нормализованную геометрию относительно кадра.
Текст и реальные ресурсные значения остаются кодом, их не запекать в ассет.

## Приоритеты оптимизации

1. Выполнено: старый `hex-sheet-bars-runes-v1.png` исключён из активного preload.
   Экономия 688055 bytes сети и4 MiB базовой текстуры; исходник сохранён в старых опытах.
2. Неиспользуемые кадры/пустоты планшетов исключить при экспорте. Например,
   tile в листе рамок и resource bar в инспекторе больше не рисуются.
3. Выпустить terrain512: гарантированное уменьшение базовой текстуры на12 MiB.
4. Подобрать tier космоса. Исходник5376 даёт63 MiB при файле156 KiB:
   сетевой размер здесь скрывает стоимость decode. Варианты шириной2048/3072/5376
   выбирать по физическому размеру слоя с запасом на движение, не только по ширине
   окна. DPR 2 и высокий канвас могут требовать старший tier. Не грузить три сразу.
5. Вынести маленькие slots/medals в компактные runtime-кадры.
6. Потестировать lossless WebP для прозрачных UI-кадров. Меньший файл не уменьшает
   decoded RGBA автоматически. Не применять lossy-сжатие к тонким золотым контурам
   без отдельной визуальной проверки.

## Скачивание, память и кеш

- Manifest должен содержать hash/version URL, пакет, размеры и список кадров.
- Для production: `Cache-Control: public, max-age=31536000, immutable` только
  для контентно-адресуемых файлов; сам manifest обновляется отдельно.
- Загружать battle-critical один раз перед входом. Дальше общий Phaser Texture
  Manager переиспользует текстуры между сценами; не уничтожать Game при каждом
  переходе. Сон/остановка Scene сами по себе не требуют повторного скачивания.
- HTTP-дисковый кеш переживает повторные открытия, Texture Manager хранит
  декодированное представление в текущей сессии. Это разные уровни.
- Не обещать вечное хранение в RAM: браузер может освобождать контекст, закрывать
  вкладку и вытеснять дисковый кеш. Нужны повторная загрузка и корректное восстановление.
- Фоны старых биомов и неиспользуемые портреты выгружать по LRU/бюджету после того,
  как сцены перестали на них ссылаться. Общий UI оставлять резидентным.
- Service Worker/Cache Storage для офлайн-режима необязателен на первом этапе.
  Не дублировать весь набор ещё и в IndexedDB без реальной необходимости.
- Текущий Lab отдаёт `no-store`; это режим разработки. Автономный снимок использует
  стандартный локальный HTTP-сервер. Production-кеширование здесь не внедрено.

## Малые экраны: 5 → 3

Профиль с тремя видимыми ожидающими участниками оставлен предложением.
Он может улучшить читаемость и свободное место. Но общий атлас рамок и плиток
останется тем же, поэтому заметной экономии этой памяти не будет. С будущими
уникальными портретами lazy-loading уменьшит число реально загружаемых изображений.
Остальных участников нужно представлять счётчиком+N, сохранив приоритет очереди.

Не менять автоматически текущий baseline; компактный профиль делать отдельной
итерацией с проверкой четырёх desktop размеров.
