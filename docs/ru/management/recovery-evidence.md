# Проверка свидетельств восстановления

Локальные restore drills PostgreSQL, MongoDB и Redis проверяют восстановление
синтетических данных. Они не устанавливают production backup и не подтверждают
согласованность снимков разных хранилищ.

`tools/ops/recovery_check.py` — проверка файлов и свидетельств последнего drill.
Она не подключается к сервисам, не создаёт backup, не удаляет файлы и не отправляет
уведомления. Пороговые значения задаёт владелец эксплуатации: у инструмента нет
выдуманных production RPO/RTO или расписания.

## Контракт manifest

JSON содержит `version: 1`, `policy` и `stores`. В `policy` обязательны положительные
конечные числа секунд:

- `max_backup_age_seconds`: допустимый возраст backup;
- `max_restore_age_seconds`: допустимый возраст проверенного восстановления;
- `max_restore_duration_seconds`: допустимая длительность восстановления.

В `stores` обязательны `site_postgres`, `game_postgres`, `mongo`, `redis`. Для каждого:

- `file`: относительный путь внутри отдельного каталога backup;
- `sha256`: SHA-256 непустого файла;
- `completed_at`: время завершения backup с часовым поясом;
- `restore.backup_sha256`: hash именно того файла, который восстанавливали;
- `restore.completed_at`: время завершения drill с часовым поясом;
- `restore.duration_seconds`: измеренная положительная длительность.

Manifest создаёт процесс резервного копирования и обновляет после успешного
изолированного восстановления. Простое заполнение этих полей человеком не
доказывает корректность восстановления: храните также отчёт проверки данных,
индексов, ограничений и версий. Manifest и backup должны быть недоступны для
изменения приложениями; проверка hash не заменяет подпись или защищённое хранение.

```sh
python tools/ops/recovery_check.py /srv/backup/evidence.json --artifact-root /srv/backup/artifacts
```

Код выхода `0` означает только успешные локальные проверки файлов, hash и времени.
`1` означает просроченный, повреждённый или неподтверждённый backup; `2` — неверный
manifest или policy. Сообщения содержат фиксированные коды без содержимого файлов,
адресов подключений и секретов. Относительные выходы из каталога и symlink за его
пределы запрещены.

## Применение перед выпуском

Назначить владельца backup и согласовать частоту, retention, RPO/RTO. Настроить
сохранение вне основного сервера, шифрование, отдельные права и проверку свободного
места. В расписании запускать backup, изолированный drill и эту проверку; ненулевой
exit направлять в существующий канал дежурного. Проверить доставку искусственным
сбоем и восстановление после него. Не устанавливать scheduler с примерными
порогами без согласованной policy.

Отдельно учесть assets, сертификаты, конфигурацию и credentials: четыре хранилища
из manifest не покрывают весь сервер. Для совместного восстановления остановить
запись по согласованной процедуре или использовать доказанный общий checkpoint.
Восстановление Redis pending не разрешает автоматический повтор игровых эффектов.
На текущем этапе расписание, offsite, retention и доставка alerts на сервере не
изменялись и не проверялись.
