# Поиск готовых кандидатов

`MonsterCandidateSearchService` в `monsters/encounters/services/candidate_search_service.py` связывает поиск определений с проверкой готовности экземпляра на заданном тире. Доступен через `monsters.public`.

Порядок: один каталог → `CatalogSearchService.search(filters)` → `MonsterBuildReadinessService.check` для каждого найденного определения → разделение на готовые и исключённые записи. Порядок каталога сохраняется, случайного выбора нет.

## Вход

`search(tier=..., filters=MonsterSearchFilters(...))`. Фильтры необязательны и сохраняют прежнюю семантику каталога: категории пересекаются, ID внутри категории являются альтернативами, обязательные теги проверяются все, системный контент исключён по умолчанию даже при прямом ID. Это внутренние фильтры Monsters. Внешний заказ встречи не принимает теги, clan/member ID или готовые фильтры; сервис подготовки сам формирует условия поиска.

Неподдерживаемый тир, включая `bool`, строку и дробное число, отклоняется до чтения каталога. Если тир поддерживается сборщиком, но недоступен конкретному монстру, запись включается в исключённые с `tier_unavailable`.

## Результат

`MonsterCandidateSearchResultDTO` — неизменяемый внутренний DTO:

| Поле | Содержание |
| --- | --- |
| `tier`, `filters` | Условия проверки |
| `candidates` | Кортеж готовых `MemberDefinition` |
| `excluded` | Полные `MonsterBuildReadinessDTO` найденных, но неготовых членов; причины находятся в `issues` |
| `unmatched_member_ids` | Явно запрошенные ID, не совпавшие с поиском по текущим условиям; без повторов |
| `matched_count` | Количество найденных до проверки готовности: готовые + исключённые |
| `empty_reason` | `None`, если есть готовые; `no_catalog_matches`, если ничего не найдено; `no_ready_candidates`, если все найденные не готовы |

`unmatched_member_ids` не означает «ID не существует»: запись могла не пройти другие фильтры или относиться к системному контенту. Сервис не раскрывает такую запись обходом правил поиска.

`excluded` содержит только найденных поиском монстров. Отчёт по каждой неготовой записи сохраняет её ID, тир, коды, пути и сообщения всех ошибок: недоступный тир, отсутствие комплекта клана, ошибочные предметы, навыки или способности. Не нужно повторно обходить весь каталог для объяснения всех несовпадений тегов.

Неожиданные ошибки зависимостей не маскируются под пустой результат. Нет запасного обращения к старому runtime, подмены клана/тира или генерации недостающего контента.

## Пример

```python
from src.backend.features.monsters.public import MonsterCandidateSearchService, MonsterSearchFilters

result = MonsterCandidateSearchService().search(
    tier=1,
    filters=MonsterSearchFilters(family_ids=("goblin_tribe",)),
)
ready_ids = [member.id for member in result.candidates]
excluded = [(report.member_id, report.issues) for report in result.excluded]
```

Для текущих гоблинов Т1 готовы все 12 определений. Запрос Т6 с тем же фильтром находит те же 12 определений, но исключает их из-за диапазона Т0–Т5: `empty_reason == "no_ready_candidates"`. Неизвестная семья даёт `no_catalog_matches`.

Это подготовка пула, а не отряд. Сервис пока не применяет количества и роли из [контракта отряда](squad_contract.md), не считает бюджет/GS, не создаёт слепки и не рассчитывает боевые параметры. База, баланс, мир и рифты не задействованы. Подготовка и выбор отряда используют этот поиск внутри домена Monsters.
