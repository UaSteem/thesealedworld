# Контракт подбора отряда

Владелец — `monsters/encounters`, контракты — `encounters/dto/selection.py`. Новый алгоритм и подключение к миру/рифтам пока не добавлены. Прежний игровой runtime остаётся отключённым.

## Ответственность

`catalog` хранит определения и ищет кандидатов. `instances` проверяет готовность и собирает бойца. `encounters` определяет состав. `inspection` показывает результат. Внутри `encounters` папки разделены на `dto`, `policies`, `services`, `resources`, `integrations`. Отдельные сервисы для миньонов и боссов не требуются.

## Запрос

`MonsterSquadRequestDTO` содержит:

| Поле | Смысл |
| --- | --- |
| `filters` | `MonsterSearchFilters`: семьи, кланы, члены, обязательные/исключённые теги, разрешение системного контента |
| `tier` | Один целый тир 0–7 для всех участников |
| `count` | `min_count`/`max_count`; для точного количества значения равны |
| `roles` | Уникальные правила ролей с `min_count`/`max_count`; отсутствующие роли запрещены |
| `selection_mode` | `random` или `specified` |
| `seed` | Обязателен в режиме `random`, запрещён в `specified` |
| `specified_members` | Упорядоченные ID для `specified`; пустой список для `random` |
| `same_clan` | По умолчанию `true` |
| `allow_repeated_members` | По умолчанию `false` |

Неверные типы, неизвестные поля и внутренне противоречивые ограничения отклоняются при создании DTO. Это ошибки запроса, а не неудачный поиск. Сумма обязательных ролей не превышает максимальный размер, а суммарная вместимость ролей допускает минимальный размер. Числа строго целые: `true`, строки и дробные значения не принимаются как тир/количество.

GS, тир игрока, локация, ID боя и сохранённых экземпляров не входят в контракт. Нет неявного профиля, который переопределяет явные ограничения. Условия источника встречи передаются как требования, без знания мира или рифта внутри Monsters.

## Результат

`MonsterSquadResultDTO` — объединение с различителем `status`:

- `selected`: исходный запрос и полный список `MonsterSquadMemberDTO` с каталоговыми `member_id`, `family_id`, `clan_id`, `variant_id`, ролью и тиром.
- `rejected`: исходный запрос и непустой список причин `code`, `path`, `message`, при необходимости `member_ids`. Частичного списка участников нет.

Успешный результат проверяет количество, разрешённые роли и их лимиты, общий тир, повторы, требование одного клана и ID-фильтры. Для `specified` порядок и количество ID совпадают с запросом. Молчаливое повышение тира, изменение роли или недобор запрещены.

DTO не читает каталоги. Существование ID, соответствие тегам и допуск системного контента должен проверять будущий сервис через поиск каталога, а наличие комплекта, навыков и способностей — через `MonsterBuildReadinessService`. Корректный DTO сам по себе не доказывает готовность контента или баланс встречи.

Выбор отряда не создаёт actor snapshot, commitment или runtime UUID. Новый результат не подменяет старый `MonsterGroupResult`, содержащий инфраструктурные данные.

## Причины отказа

| Код | Смысл |
| --- | --- |
| `no_candidates` | Нет кандидатов по фильтрам |
| `tier_unavailable` | Нет подходящих кандидатов на запрошенном тире |
| `members_unbuildable` | Кандидаты не проходят проверку сборки |
| `insufficient_distinct_members` | Недостаточно разных бойцов при запрете повторов |
| `role_requirements_unmet` | Не обеспечиваются обязательные роли или их количества |
| `count_requirements_unmet` | Невозможно обеспечить размер отряда |
| `clan_constraint_unmet` | Нельзя собрать состав в одном клане |
| `specified_member_unavailable` | Конкретный боец недоступен |
| `constraints_unsatisfiable` | По отдельности допустимые ограничения несовместимы вместе |

При отказе ограничения не ослабляются и старый сборщик не используется как запасной. Коды закреплены контрактом; назначение причин — ответственность будущего алгоритма.

Это примеры DTO, а не активные настройки спавна или подтверждённые профили сложности.
