# Seed мира, рифтов и встреч

Это согласованная схема будущих потребителей. Подключения World/Rift и генерации их seed в текущем изменении нет.

## Владение seed

- Мир получает основной seed один раз при создании мира.
- Регион получает производный seed из seed мира и стабильного ID региона.
- Мировая встреча получает производный seed из seed региона, стабильного ID точки и номера обновления населения этой точки.
- Каждый экземпляр рифта получает собственный случайный seed, независимый от seed мира. Повторный запрос создания того же экземпляра должен использовать уже сохранённое значение.
- Встречи внутри рифта получают производные seed из seed экземпляра рифта и стабильного ID встречи.

При повторном запросе существующей встречи её seed не меняется. Новый номер обновления мировой точки или новый экземпляр рифта позволяет получить новый состав. Не следует использовать текущее время, один хеш игрока или новый случайный seed при каждом чтении встречи.

Производные seed следует получать стабильным хешированием с разделением назначений (`world-region`, `region-encounter`, `rift-encounter`) и однозначным кодированием исходных компонентов. Встроенный Python `hash()` не подходит: его значения могут меняться между процессами. Точный формат кодирования и версию функции необходимо определить при реализации владельца; сейчас утилита хеширования не добавляется.

## Граница Monsters

Monsters получает готовый целочисленный `seed` в `MonsterEncounterOrderDTO`. Ему не передаются seed мира/региона/рифта, ID игрока или тип вызывающего домена. Он не генерирует и не сохраняет seed за заказчика.

Одинаковый seed гарантирует повторяемость только вместе с теми же параметрами заказа, каталогом, профилями, формулами GS и алгоритмом выбора. Изменение GS игрока может изменить состав при неизменном seed. Для существующей встречи владелец должен сохранять её заказ и выбранный состав; операционный лог не является хранилищем игрового состояния или гарантией воспроизведения после обновлений кода.

## Логи сборки

`MonsterEncounterSelectionService.select()` пишет структурированные события через общий Loguru:

| Событие | Уровень | Содержание |
| --- | --- | --- |
| `MonsterEncounterSelectionRequested` | DEBUG | Начало, `selection_id`, UTC `requested_at`, тип, тир, семьи, seed, сложность, режим, GS игрока |
| `MonsterEncounterSelectionCompleted` | INFO | Все поля заказа выше, UTC `completed_at`, `duration_ms`, статус, конфигурация, бойцы с ID/кланом/ролью/тиром/ценой, коды отказа, источник/ID профиля, ID ядра и бюджет: базовый, бонус, итог, расход и остаток |
| `MonsterEncounterSelectionFailed` | ERROR | Контекст заказа, время и длительность, traceback неожиданной ошибки; исключение передаётся вызывающему коду |

В production DEBUG может быть отключён. Завершающее INFO всё равно содержит параметры заказа и время его начала, поэтому информация о завершённом заказе не зависит от DEBUG. Ожидаемый отказ (`rejected`) — обычное завершение с кодами причин, а не техническая ошибка.

`selection_id` — новый операционный UUID для каждого вызова, не seed и не ID игрового отряда. Он не меняет генератор случайных чисел сборщика. Общий контекст логирования может дополнительно содержать HTTP request ID. Прямые вызовы сервиса логируются так же, без обязательной зависимости от HTTP.

Пишутся только явно выбранные поля игрового заказа и состава: заголовки, ключи доступа, сырые HTTP тела, имена игроков и тексты описаний не копируются. Невалидный внешний DTO отклоняется API до входа в сборщик и не считается заказом на сборку.

Логи используют существующие sinks приложения; отдельные таблицы, файлы аудита и новые хранилища не создаются. Проверки находятся в `tests/backend/features/monsters/encounters/test_selection_logging.py`.
