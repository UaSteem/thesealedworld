# Изображения, лор и раскрытие Items

Меч T0–T5 подключён к генерации, публичному каталогу и инвентарю в исходном коде.
Двенадцать прозрачных WebP опубликованы в S3. Для рабочей БД требуется миграция `0003_item_identification`.
В рамках реализации миграция не применялась, приложение не развёртывалось.
Решение о будущем выборе и сохранении варианта: [ADR-0001](../../../../adr/0001-item-visual-selection.md).

## Источник и поиск

Python-источник: `src/backend/features/items/resources/visuals/sword.py`.
Pydantic-модели: `src/backend/features/items/dto/visuals.py`.
Модуль `resources/visuals/__init__.py` собирает определения и словари:

- `BASE_VISUAL_SET_IDS["sword"]` → `"sword.basic"`;
- `VISUAL_SETS_DB["sword.basic"]` → набор с базами и вариантами;
- `VISUAL_VARIANTS_DB["sword.basic.iron.t1"]` → материал, тир материала, состояние и путь к SVG.

Одна база сейчас ссылается на один набор; набор может использоваться несколькими механическими базами.
Варианты внутри набора имеют глобально уникальные ID. Несколько вариантов одного материала и тира допустимы.
Индексы строятся после проверки дубликатов; отдельные независимые копии определений не поддерживаются.
Модели запрещают неизвестные поля и изменение полей после создания. Производные словари доступны только для чтения по соглашению, технически это обычные Python `dict`.

## Меч

| Тир материала | Материал | Состояние |
| --- | --- | --- |
| T0 | `mat_scrap_metal` | `worn` |
| T1 | `mat_iron_ingot` | `clean` |
| T2 | `mat_cobalt_ingot` | `clean` |
| T3 | `mat_mithril_ingot` | `clean` |
| T4 | `mat_adamantite_ingot` | `clean` |
| T5 | `mat_thorium_ingot` | `clean` |

`condition` описывает рисунок, не механическую прочность предмета.
`material_tier` соответствует тиру материала, не редкости. Характеристики, коэффициенты и названия материалов берутся из существующего Items.
`source_path` — относительный путь от корня репозитория, не публичный URL. Палитры остаются художественными пробами.
У текущих шести вариантов нет ограничений по аффиксам.
`ItemVisualService.select()` фильтрует набор по материалу, тиру и `required_lore_tags`.
Среди подходящих вариантов предпочтение получают варианты с большим числом требуемых признаков.
Одинаково подходящие варианты выбираются отдельным генератором случайных чисел. Механические броски при этом не меняются.
При отсутствии изображения остаётся прежняя общая иконка.

## Явная проверка

```python
from src.backend.features.items.resources.visuals import ITEM_VISUAL_CATALOG, VISUAL_VARIANTS_DB
from src.backend.features.items.services.catalog_service import ItemCatalogService

items = ItemCatalogService.load_default()
ITEM_VISUAL_CATALOG.validate_item_references(items.base_items, items.materials)
variant = VISUAL_VARIANTS_DB["sword.basic.iron.t1"]
payload = variant.model_dump(mode="json")
```

Структурная проверка при сборке каталога запрещает повторные ID наборов, вариантов и привязки базы.
Явная проверка выше проверяет существование баз и материалов, совпадение тира и допустимость материала для каждой базы набора.
Она не обращается к БД, не читает файлы, не выбирает изображение и не создаёт экземпляр предмета.
Наличие исходников, SHA и соответствие рабочему JSON проверяют целевые тесты.

`assets/item_art/variants/sword/variants.json` остаётся рабочим описанием ассетов. Серверные определения его не читают.
Тест сопоставляет оба описания, чтобы расхождения обнаруживались явно.
`ItemCatalogService.load_default()` загружает механические определения. `ItemGenerationService` отдельно подключает `ItemVisualService`.

## Генерация и лорные признаки

Порядок: база → материал → тир материала → масштабирование и аффиксы → изображение → сохранение экземпляра.
`material_tier` в запросе позволяет явно выбрать тир материала. Явные `material_id` и `material_tier` должны совпадать.
`rarity_tier` сохраняет прежнее назначение grade/редкости и прежнюю подсказку автоподбора материала, когда явный тир отсутствует.
Фактический материал определяет `item_tier`. Редкость не переопределяет тир явно выбранного материала.

Контролируемый словарь расположен в `resources/affixes/narrative.py`.
Существующее `descriptive.narrative_tags` ссылается на его устойчивые ID.
`normalize_lore_tags()` собирает отсортированные уникальные признаки только по ID фактически выпавших аффиксов.
Числовые значения, порядок и повторения не меняют лорный набор.
Широкие `narrative_tags` предмета сохранены для существующих потребителей; это другой набор.

Текстовый шаблон остаётся в `item_generated_templates`. Хеш v2 учитывает версию промпта, клан, базу, материал и его тир.
Дополнительно учитываются нормализованные лорные признаки и выбранный `visual_variant_id`.
ID экземпляра, числовые броски и сырые данные контекста в идентичность шаблона не входят.
Промпт получает смыслы признаков и описание выбранной внешности.

## Хранение и раскрытие

`item_instances` хранит механику, износ, материал, `appearance` и `is_identified`.
`appearance.visual_variant_id` сохраняется при создании; чтение и открытие инвентаря не повторяют выбор.
Новые экземпляры и ещё не подготовленные текстовые шаблоны сохраняют `name/description=NULL`.
Базовое представление вычисляется из Python-каталога. Ответ ИИ заполняет общий шаблон.

До определения сервер выдаёт только базовое имя и описание.
Действие инвентаря `identify` проверяет владельца, состояние и доступность предмета, затем сохраняет флаг раскрытия.
Если ИИ ещё работает, остаётся базовое представление. Последующие чтения подхватывают готовый текст из БД.
Готовность ИИ не устанавливает `is_identified`. Скрытый текст не передаётся в публичные DTO, HTML или кеш каталогов.
Навык оценки пока не реализован.

Миграция `src/backend/alembic/versions/0003_item_identification.py` добавляет флаг и допускает пустые тексты.
Существующие строки и тексты сохраняются. Применение к рабочей БД является отдельной операцией.

## Два размера и S3

Для каждого варианта создаются прозрачные lossless WebP:

- `thumbnail`: 96×288 пикселей для экипировки;
- `image`: 256×768 пикселей для инвентаря и карточки.

Иконки вписываются через `object-fit: contain`. Меч занимает сетку 1×3.
Ключи `items/sword/<visual_variant_id>/<sha256>.<вид>.webp` зависят от содержимого.
Описание двух объектов хранится в Python-модуле `resources/visuals/sword_renders.py`.
Публикация использует существующий `S3GeneratedAssetStorage`; существующие объекты по тем же ключам пропускаются.
Frontend `/static/generated-assets/<key>` использует существующий S3-reader и перенаправляет браузер на объект.
Игровые файлы не копируются в frontend static.

```powershell
.venv/Scripts/python.exe -m tools.assets.item_visuals build
.venv/Scripts/python.exe -m tools.assets.item_visuals publish --dry-run
.venv/Scripts/python.exe -m tools.assets.item_visuals publish
```

Для сборки нужны Node.js и Sharp. При необходимости задайте `--node` и `--sharp-module`.
Сборка пишет растры в `assets/item_art/renders/` и Python-описание объектов. JSON используется только как транспорт сборщика.
`publish --dry-run` проверяет файлы локально и не обращается к S3.

## Bootstrap и интерфейс

Существующий GameCatalog bootstrap содержит типизированный раздел `item_visuals` и его хеш в manifest.
В IndexedDB попадают базовые тексты, ID и два публичных URL. Исходные пути и подготовленный приватный лор не выдаются.
Экипировка использует миниатюру, рюкзак и карточка — крупное изображение.
У занятого слота скрыта подпись слота; название предмета доступно в карточке и подсказке.
Пустые слоты сохраняют локальные SVG и подписи. Эти интерфейсные иконки не требуют переноса в S3.

Preview без игровой БД:

```powershell
.venv/Scripts/python.exe -m tools.game_preview.render --fixture inventory/swords --serve
```

Preview использует тот же S3-reader. Перед проверкой пересоберите игровые CSS/JS штатным static compiler.
Для следующего предмета добавьте SVG, Python-набор, два растра, S3-ключи и проверки.
Новая механика выбора для каждого типа предмета не требуется.
