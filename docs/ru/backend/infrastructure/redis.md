# Redis

## Восстановление backend Redis Streams (A05-05)

У backend bus исторически читались только новые сообщения (`XREADGROUP >`).
После ошибки или остановки worker сообщение оставалось в pending entries list
(PEL). Исход обработки может быть неизвестен: эффект в SQL/Redis/Mongo мог уже
произойти, даже если ACK не дошёл. Автоматически повторять такие handlers нельзя.

Recovery сохраняет зависшую доставку в quarantine hash для сверки оператором и не
вызывает бизнес-обработчик повторно. Сохраняются исходные stream/group/message ID
и raw fields; если тело уже удалено старым trim, сохраняется явная отметка потери
payload. ACK исходной доставки допустим только после сохранения quarantine.
Карантин означает «исход неизвестен», а не «ошибка до начала обработки».

Ключ: `<game_stream_name>:quarantine:<consumer_group>`, поле hash — исходный
message ID. Значение — JSON envelope с raw payload и метаданными доставки.
Чтение — `HSCAN` небольшими порциями или `HGET` для конкретного ID. `HSETNX`
не перезаписывает сохранённый исход при повторной попытке после ошибки ACK.

Настройки backend (в том числе chat runtime на общем потоке):

- `stream_pending_min_idle_ms`: 300000 по умолчанию, положительное число.
- `stream_pending_scan_count`: 100 по умолчанию, от 1 до 1000.

Каждое чтение новых событий сопровождается ограниченной по числу записей
проверкой PEL; cursor проходит всю очередь, включая сообщения других consumers.
Порог idle — основание сохранить неизвестный исход, не доказательство смерти worker.

Проверка pending и сохранение выполняются Redis Lua script без конкурентного
вмешательства между командами. Это не общая транзакция с SQL/Mongo и не гарантия
exactly-once бизнес-эффектов. Старый медленный handler может завершиться уже после
переноса его pending-записи: повтор всё равно требует проверки результата.

Семантика Redis: [XPENDING](https://redis.io/docs/latest/commands/xpending/),
[XACK](https://redis.io/docs/latest/commands/xack/),
[Lua execution](https://redis.io/docs/latest/develop/programmability/eval-intro/).

## Разбор quarantine

1. Установить исходные stream/group/message ID и тип события. Не публиковать
   payload в общие логи: он может содержать пользовательские данные.
2. Проверить фактический результат у владельца операции в SQL/Redis/Mongo.
   Отсутствие ACK не доказывает, что результат отсутствует.
3. Если эффект подтверждён — документировать reconciliation без повторной выдачи.
   Если исход неизвестен — не выполнять автоматический повтор.
4. Повтор допустим только через согласованный доменный контракт с доказанной
   идемпотентностью; общий replay CLI в этом исправлении не предоставляется.
5. Архивировать/удалять quarantine только после принятого решения по событию.
   Tombstone с отсутствующим payload не является восстановленным событием.

Recovery не исправляет handlers, которые проглатывают ошибку и возвращают success,
и не восстанавливает payload, удалённый раньше. End-to-end business recovery
остаётся отдельной задачей для каждого затронутого доменного контракта.

## Retention

Автоматический `MAXLEN` для shared game stream отключён: он мог удалить тела
pending и ещё не прочитанных сообщений разных consumer groups. Лимит
`game_stream_maxlen` не должен считаться гарантией ограничения памяти bus.
Quarantine также не очищается автоматически и не имеет короткого TTL.

До отдельной group-aware retention policy общий поток и quarantine могут расти.
Нужны контроль памяти Redis, сверка pending/quarantine и согласованная очистка;
не запускать слепой `XTRIM MAXLEN` для устранения backlog. Политика хранения
chat buffer не изменяется этим исправлением.


## Локальная проверка recovery

Изолированные Redis adapter/lifecycle tests запускаются явно:

```powershell
$env:RUN_STREAM_RECOVERY_REDIS_TESTS='1'
.venv/Scripts/python.exe -m pytest tests/backend/core/bus --no-cov -q
```

Fixture создаёт отдельный `redis:7-alpine` container без volume/persistence,
с уникальным именем и случайным loopback port, затем удаляет его в `finally`.
Настройки реального приложения не используются. Проверяется отмена обработки
и повторное создание runtime, а не принудительное завершение OS-процесса или
восстановление Redis после потери диска. Сохранность quarantine при потере Redis
зависит от его persistence/backup policy и здесь не аттестуется.
