# Инвентаризация экранов для переноса игрового интерфейса

Дата: 2026-10-26. Этап 0 плана `tasks/active/2026-10-26-game-ui-runtime-migration.md`.

Проверены исходники текущего рабочего дерева. Наличие маршрута или DTO ниже не означает, что сценарий проверен на запущенном сервере. Запросы не выполнялись; данные персонажей, Backend и действующие экраны не изменялись.

## Правила чтения

- **Runtime-источник** — существующий frontend/typed client, который следует сохранить или адаптировать.
- **Lab-донор** — новое визуальное представление; его mock-значения и локальные действия не являются игровым контрактом.
- **Нужно сверить** — проверка перед зависимой реализацией. Новый контракт не считается согласованным.
- Сцены работают в одном Phaser.Game. Источником игрового состояния остаётся Backend; HTML-статус и чат сохраняются, глобальная правая панель снимается.

Пути в таблицах приведены относительно корня репозитория. Число после двоеточия — проверенный ориентир в исходнике на дату инвентаризации; оно может измениться при дальнейшем переносе.

## 3. Проверенные разрывы и вопросы перед зависимой реализацией

Это список для решения владельцем на соответствующем этапе, не разрешение менять Backend.

1. **Стартовый handoff.** Создание инициализирует `awakening_rift` (`src/backend/features/game_lobby/services/character_creation_service.py:87`). Финальное активное действие `enter_prepared_rift` отклоняется (`src/backend/features/scenario/services/scenario_service.py:202`). Новый рифт должен заменить этот переход своим поддерживаемым runtime. В отдельном tutorial finalize остаётся выбор окраины (`handlers/tutorial_handler.py:63`), который не совпадает с желаемым первым выходом в город. Это не исправляется новым шаблоном.
2. **Пояс в бою.** Inventory-контракт содержит belt/quick_slots. Доступность read-пути во время боя и точное представление вещей в combat/status требуют проверки. Нельзя объявлять отсутствие всех данных или расширять статус только по отличию нового макета.
3. **Параметры разговора и текстового квеста.** ScenarioPayloadDTO имеет `status_bar`, `ui`, `extra_data`, но не отдельную типизированную универсальную таблицу всех показателей нового макета. До расширения контракта проверить фактический payload конкретного сценария и то, что уже передаётся в этих полях. Не рисовать `Доверие +12` из Lab, если сервер этого не вернул.
4. **Билды и журнал.** Старые представления прямо называют эти возможности черновиком/будущими. Новые вкладки Lab не доказывают backend CRUD. Нужна инвентаризация конкретных планируемых операций, затем либо поддерживаемый существующий запрос, либо честная недоступная вкладка. Универсальный новый API этим документом не вводится.
5. **Кварталы и вложенные услуги.** Текущие city-services DTO и actions не содержат утверждённой модели трёх строек, прогресса/стоимости/сброса, player shop list/покупки, участка/дома. Поиск выполнялся по frontend routes/typed clients и shared schemas; это не вывод об отсутствии всех заготовок во всём Backend. До отдельной реализации функции показывать недоступными. ADR-0002 задаёт направление, а не runtime.
6. **Добыча.** В текущем frontend найден claim-all; новый «забрать предмет» требует подтверждённого контракта. `src/backend/features/game_session/integrations/session_integrator.py:195` формирует claims и ставит `loot_claim_task` в очередь; queued ответ не равен владению предметом. Состояние интерфейса должно сохранять ожидание и сверять фактический inventory после worker. Полный проход через worker в этой инвентаризации не проверялся.
7. **Мир.** CityDraft покрывает только квадратный донор D4. Внешние локации, encounters/attack/bypass/interact/corpses необходимо сохранить либо перенести явно. Нельзя архивировать весь Exploration, объявив новую карту города заменой всему миру.
8. **Данные новой боевой композиции.** Текущие DTO уже дают actor cards, stat sheets, очередь, события и exchange state. Для анимаций и удалённых целей сначала сопоставить реальные доступные поля и их свежесть; не объявлять весь контракт непригодным по виду Lab и не добавлять WS автоматически. Отсутствующие поля или операции документируются отдельно с потребителями/рисками.

## 4. Что нельзя архивировать одним движением

- `templates/game/base_game.html`, `session_content_inner.html` и `static/js/core/game_shell.js` объединяют несколько доменов, status, menu, modal и chat. Пока остаётся их потребитель, нужна составная активная версия.
- `game_features/session/services/session_context_builder.py` и `response_director.py` — orchestration и API boundary, не «старая верстка». Их меняют ограниченными slices и не заменяют Lab boot.
- `templates/game/domains/exploration/viewport/main.html` обслуживает город, внешние места и встречи. Снятие разрешено только после покрытия всех поддерживаемых веток.
- `templates/game/domains/city_services` разделяется таверной/порталом/прочими сервисами; совпадение нового фона с кварталом не устраняет всех потребителей.
- `static/js/core/realtime_supervisor.js`, `game/includes/chat_overlay.html`, csrf/auth/token code — действующие общие механизмы, не mock-доноры.
- Общие CSS/theme/fonts/vendor/icons, старые D4 tiles и API/shared DTO сохраняются, пока используются. При смене presentation нельзя архивировать бизнес-логику и контент сценариев вместе с шаблоном.
- Старый frontend death/loot связан с session routes; удаление самостоятельного каталога не является полным переносом. Результаты/claim/respawn и их delayed side effects проверяются отдельно.
- Список Lab scene keys и `openDraft` — инструмент стенда. В runtime он не публикуется как обход серверных состояний. `app.py`, frozen JSON, тестовый reset демо и standalone servers не переносятся.

## 5. Сборка и жизненный цикл: условия первого переноса

- `src/frontend/static/css/compiler_config.json:24` собирает `game.js` из `core/catalog.js`, `core/exploration_cooldown.js`, `core/game_state_loader.js`, `core/game_shell.js`, `core/main.js`, `core/realtime_supervisor.js`. Это не независимый исходник для ручного редактирования. `:7` связывает `game_bundle.css` с `game.css`; стили меняются в исходных импортируемых файлах. Сохранить одновременно конфигурацию, входные bundle-файлы и старые compiled outputs для воспроизводимости архива.
- `src/frontend/static/js/core/game_state_loader.js:67` вызывает `GameStates[state].init(root)`; `:93–94` повторяет запуск на `htmx:load` и `htmx:afterSwap`. До размещения Phaser host определить его устойчивого владельца и teardown: обычный session swap не должен удалять живой Game или оставлять обработчики прежней сцены.
- `src/frontend/templates/game/session_content_inner.html:7` содержит заменяемый `game-session-root`. `ResponseDirector` возвращает то полный session fragment, то viewport, а routes сценария иногда требуют redirect. Простая вставка Lab boot в этот root не является готовым lifecycle-решением.
- Многие текущие browser routes возвращают HTML, хотя typed Backend client уже получает DTO. Для Phaser можно адаптировать представление ответа на существующей frontend-границе, не меняя Backend DTO и не выдавая браузеру game access token. Конкретный frontend response/boot envelope проектируется на этапе оболочки. Это frontend-only возможность; она не разрешает придумывать отсутствующие игровые поля.
- Существующий `/api/game/character-status` уже отдаёт JSON. Не вводить второй источник статуса лишь потому, что остальные старые действия ещё HTML. Не отключать существующие auth/CSRF/realtime, пока новый client lifecycle не проверен в их присутствии.

### Сборка и кеш: фактические точки запуска

`src/frontend/core/static.py:16` экспортирует `compile_static_assets(minify=False)`. Он вызывает внешний `codex_core.dev.static_compiler.compiler.StaticCompiler` с `minify` и `remove_comments=not minify` (`:28–38`), передаёт `compiler_config.json`, CSS_DIR и JS_DIR. Исходники самого shared compiler в этой инвентаризации не менялись и его внутренняя логика не проверялась.

Поддерживаемые локальные точки запуска:

```powershell
.venv/Scripts/python.exe -m src.frontend.manage compile
.venv/Scripts/python.exe -m src.frontend.core.static
```

Первая использует `minify=not settings.debug` (`src/frontend/manage.py:24–30`, ветка CLI `:65`); вторая вызывает `minify=False` (`src/frontend/core/static.py:49–51`). Эти команды создают/обновляют compiled outputs, поэтому **на этапе 0 они не запускались**. Комментарий в static.py упоминает lifespan, но проверенный `src/frontend/app.py:97–161` не вызывает compiler: запуск сервера сам по себе здесь не доказывает пересборку. Внешнюю сборку при релизе проверять отдельно; конфигурацию окружения не выводить из комментария.

`src/frontend/core/renderer.py:40` передаёт `static_version`. `_static_version()` (`:106–126`) вычисляет максимум целочисленных mtime нескольких compiled CSS/JS и `js/game/scenes/hex_map_scene.js`, а не хеш всех новых модулей/ассетов. `base_game.html:23–28` и `:38` используют `?v={{ static_version }}`. Поэтому новый standalone scene/module/atlas нельзя считать автоматически покрытым invalidation: при переносе нужно согласовать его включение в действующий loader/version contract. Замена текста исходного модуля без пересборки/правильной версии может оставить старый bundle у клиента.

`src/frontend/app.py:79–92` кеширует `inline_css` в процессе, только когда `settings.debug` ложно. В debug читает файл заново. Возврат старого compiled файла без учёта процесса/кеша не является доказанным возвратом клиентского вида. Ничего из этого не требует менять Backend-контракт игры, но требует проверки frontend build/lifecycle.
