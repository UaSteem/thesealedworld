# Локальная проверка кривой баланса монстров

`tools/monsters/simulate_balance_chain.py` запускает настоящий in-memory Combat executor/resolver без записи в БД и без API генерации. Это диагностический сценарий, а не новая игровая формула.

## Повторный запуск

```powershell
.venv/Scripts/python.exe tools/monsters/simulate_balance_chain.py --workers 3 --output var/balance-chain-goblin-sneak-2026-10-17
```

По умолчанию: миньон `goblin_tribe.base.goblin_sneak`, тиры 0–5, количества 1–6, по 100 боёв, предел 100 раундов. У игрока 16 предметов соответствующего тира, исходные характеристики стартового слепка двух клинков и навыки фехтования, парного оружия и лёгкой брони: 20% на Т0, далее +10 п.п. за тир. Ранг симбионта следует существующему примеру Studio: `max(1, player_tier + 1)`.

Игрок начинает против монстров своего тира. После полного перебора количеств тир монстра повышается. Если все количества дали 100 поражений из 100, повышается тир игрока; для нового игрока проверка снова начинается с его тира. Достижение максимального тира монстров тоже завершает текущую ступень игрока. Дополнительно записываются первые количества, при которых проиграны все бои, включая отдельный порог для штатного диапазона отряда.

Для обычных гоблинских встреч easy/normal профиль допускает 2–5 существ. Количества 1 и 6 — диагностические. Группа состоит из одинаковых миньонов; это проверка количества, а не исполнение весового подбора смешанного отряда. В JSON сохранены профиль, весовые настройки и поправка бюджета за количество. Эти бюджетные настройки не являются дополнительным множителем боевых характеристик.

## Файлы и воспроизводимость

В выходной папке лежит сводный `summary.json`. Для каждого случая `p0-m0-n1` и аналогичных сохраняются `inputs.json`, `summary.json` с исходами всех боёв и `sample-combat-log.json`. Результаты записываются сразу после завершения случая. Повтор той же команды продолжает незавершённый прогон; несовместимая конфигурация, изменённый Python-код или изменённые входы требуют новой выходной папки.

Параметры `--member-id`, `--mastery-start`, `--mastery-step`, `--max-count`, `--battles`, `--max-rounds`, `--seed`, границы тиров и `--workers` позволяют повторить сценарий. Временные результаты лежат в `var/`; для сохранения отчёта используйте экспорт в `outputs/`.

Симуляции выполняются с отдельным seed для каждого боя, свежими независимыми актёрами и полными ресурсами. Процессы изолируют глобальный RNG движка. Порядок ID игрока чередуется. Ничьи и остановки по пределу раундов не засчитываются как победы.

## Excel

`tools/monsters/report_balance_chain.mjs` строит книгу из сводки и сохранённых сборок:

```powershell
& '<bundled-node>' tools/monsters/report_balance_chain.mjs var/balance-chain-goblin-sneak-2026-10-17/summary.json outputs/balance-chain-2026-10-17
```

Используется bundled `@oai/artifact-tool`: путь Node.js и каталог зависимостей определяются через `load_workspace_dependencies`; в выходном каталоге требуется `node_modules` junction на этот каталог. Листы: сводная таблица и графики, все серии, характеристики сборок и ограничения. Непроверенные сочетания тиров остаются пустыми.

## Результат первого прогона 17.10.2026

Проверены 96 сочетаний, всего 9 600 боёв. Все завершились по боевому исходу, предел 100 раундов не достигался; максимальная наблюдаемая длительность — 24 раунда. Формулы и коэффициенты не менялись; для монстров Т5 используется согласованный множитель ×4.

В этом сценарии способность игрока справляться с группой своего тира падает, несмотря на рост навыков. Это основание исследовать вклад тирного роста и экипировки, а не автоматически переносить конкретный процент побед на будущий бой с активными действиями.

## Границы выводов

Обе стороны управляются существующим локальным ИИ. Активные финты и магические способности в этом сценарии не добавляются, стартовые тактические токены нулевые; обычные навыки, триггеры оружия и экипировки сохраняются. Статы игрока вне предметных бонусов не растут с тиром. Один фиксированный комплект на тир не представляет все возможные сборки. Известное отсутствие применения капа остаточного сопротивления в resolver здесь не исправляется. Результаты показывают текущую механику и помогают выбрать следующую проверку, но не доказывают баланс будущего полного боя.
