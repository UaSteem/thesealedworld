## Исходный запрос и уточнения

Пользователь просит «составим план переделки всего игрового CSS на токены», оставить «Тёплое приключение» по умолчанию, сохранить старую цветовую гамму вторым набором токенов без подключения и исправить навык работы со стилями игры. Названия токенов постоянны; при смене темы меняются значения. Обсуждение относится ко всей игре, не только к инвентарю.

Целевая композиция: слева постоянная HTML-панель персонажа, справа игровое поле и HTML-чат под ним. В центральном поле позже выбирается технология конкретного экрана; бой на Phaser пока идея. Основа оформления — Rift Lab, но экспериментальный рифт пока не переносится. При возврате к миру сохраняется кеш графики, а данные запрашиваются актуальные.

## Целевой контракт

### Слои и владельцы

| Слой | Ответственность | Что не переносится сюда |
| --- | --- | --- |
| Общие game-токены | Шкалы размеров/отступов/типографики, длительности, семантические роли | Разметка страниц и доменные правила |
| Тема | Значения стабильных ролей цвета, шрифтов, рамок, теней; при необходимости декоративные ресурсы | Сетки экранов и breakpoints |
| Game CSS | Компоненты, состояния, размеры через токены, расположение и адаптивность | Локальные копии палитр |
| HTML shell | Постоянный персонаж, чат, контейнер центрального экрана | Экспериментальные lab-контролы и фиктивные данные |
| Phaser | Сцены, графика, input, масштаб и кеш текстур | Прямая работа с игровыми БД, авторитетное состояние |
| JS-адаптер темы, будущий | Чтение нормализованных game-токенов для canvas, обновление активных сцен | Второй независимый набор цветовых значений |

Сохранить пригодные текущие имена (`--col-*`, `--font-*`, shell-токены). Переименовывать только при доказанном конфликте смысла, с таблицей миграции. Базовые шкалы → семантические роли → небольшое число компонентных токенов. Не превращать каждый локальный `0`, процент, коэффициент или формулу сетки в токен.

Тема и плотность интерфейса — разные настройки. Цветовая тема не должна менять breakpoint или переставлять чат. Responsive CSS выбирает композицию и при необходимости переопределяет размерные токены. Media-query условия задаются правилами сборки/CSS: обычный `var()` не является универсальным значением для условия `@media`.

Целевая сборка: отдельный исходный theme entry → `theme.css`, существующий `game_bundle.css` → `game.css` с правилами компонентов и раскладок. Имена нового исходного entry и точное расположение файлов уточнить по реальному сборщику на этапе 1. Общие размерные токены можно включить в theme/token entry, но не дублировать в двух результатах сборки. В шаблонах загрузить theme перед game, исключить повторные импорты прежних палитр из game. Сборка производится при разработке/релизе. Смена поддержанной темы меняет атрибут на корне game-оболочки и значения переменных, без сборки и загрузки индивидуального bundle.

Adventure загрузить как единственный активный набор. Classic хранить отдельным исходным набором, исключённым из активных entry, шаблонов и пользовательского выбора. До будущего подключения можно проверять его отдельным preview fixture. Историческую палитру сохранять не только по `game/core/tokens.css`: учесть переопределения в компонентах, inline CSS и JS. Цвета ресурсов, редкости, опасности, focus и disabled должны иметь полное сопоставление с ролями; при новом токене определить значение для обоих наборов. Фактический переключатель нескольких тем — отдельный последующий шаг.

### Оболочка и центральное поле

На desktop — слева статус/экипировка, справа поле и чат под ним. Текущий фокус: 2560×1440 и выше, 1920×1080, нижняя граница 1366×768; отдельно учитывать уменьшенную высоту окна браузера. Статус и чат сохраняют компоненты/состояние между игровыми экранами. Мобильная и планшетная версии отложены; старые mobile-only стили/поведение выводятся в архив с картой происхождения. Общие desktop-компоненты, даже с историческими mobile-* именами, сохраняются. Будущий телефон ориентирован на landscape, сворачиваемый чат и меньшую видимую высоту мира без уменьшения масштаба объектов; это не критерий текущего этапа.

Переносить оболочку из Lab с реальными frontend view models/API. Не переносить генератор рифта, экспериментальную сцену, debug-кнопки, локальный стенд, mock-персонажа или фиктивный чат в runtime. Выбор HTML/Phaser для каждого центрального экрана фиксировать отдельно; игра не обязана переводить любой текстовый экран в canvas.

Phaser не применяет CSS-переменные автоматически. Будущий адаптер читает явный перечень токенов, валидирует/нормализует CSS-цвета и единицы, ожидает загрузку шрифтов, передаёт обновление активным сценам. DOM-подсказки в portal-контейнерах тоже должны получать game-тему; ограничение темы корнем оболочки не должно оставить tooltip на старой палитре. Сайт и кабинет сохраняют собственные поверхности.

600×600 — допустимая логическая сцена. `FIT` сохраняет пропорции и композицию, но может оставлять поля. При доступной ширине 360 её масштаб 0,6: текст 16 становится визуально 9,6 px, кнопка 44 — 26,4 px. `RESIZE` подстраивает размер canvas под контейнер, но требует переразмещения объектов. Поэтому проверять читаемость, touch targets и ориентацию; для карты отдельно управлять камерой, для HUD/инвентаря — адаптивной композицией. Режим выбрать после пробы, а не закреплять 600×600 как универсальный стандарт.

Справка: [Scale Manager](https://docs.phaser.io/phaser/concepts/scale-manager), [Scenes and global caches](https://docs.phaser.io/phaser/concepts/scenes), [DOM Elements](https://docs.phaser.io/phaser/concepts/gameobjects/dom-element).
