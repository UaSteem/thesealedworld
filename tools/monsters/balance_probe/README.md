# Универсальная проверка баланса Monsters

Запускать из корня репозитория через `.venv/Scripts/python.exe -m tools.monsters.balance_probe`.
Инструмент использует действующий контракт Monsters и настоящий симулятор Combat, без HTTP, Redis и записи в БД.
Он не меняет каталог, цены, характеристики или формулы.

## Встречи из встроенных профилей

```powershell
.venv/Scripts/python.exe -m tools.monsters.balance_probe --player starter_dual_blades_01 --family goblin_tribe --tier 0 --encounters ordinary patrol guard leader --difficulty easy --battles 50 --feints both --seed 0 --output var/balance-probe/goblin-starter-easy
```

`--difficulty easy normal hard` проверяет все три сложности. `--battles` — число боёв **на каждую комбинацию** игрока, типа встречи и сложности. Seed идут последовательно от `--seed`.

## Фиксированный отряд и сравнение билдов

```powershell
.venv/Scripts/python.exe -m tools.monsters.balance_probe --mode fixed --player starter_dual_blades_01 starter_guard_01 --family goblin_tribe --tier 0 --member goblin_tribe.base.goblin_scavenger=2 --member goblin_tribe.base.goblin_slinger=1 --battles 50 --feints both --output var/balance-probe/archer-matchups
```

Указывается полный ID представителя и количество. Проверяются семья, готовность и тир; фиксированный состав содержит от 1 до 8 монстров. Навыки разных стартовых билдов могут различаться: отчёт предупреждает об этом.

## Сохранённые игроки

```powershell
.venv/Scripts/python.exe -m tools.monsters.balance_probe --player-input var/starter-full-t0-relative-feints/inputs.json --player-key starter --player-key full --tier 0 --difficulty easy normal hard --battles 50 --feints both
```

Без `--player-input` стартовый слепок собирается из текущего каталога. С `--player-input` используется явно сохранённый снимок: старые предметы автоматически не пересоздаются. При нескольких игроках в файле обязательны `--player-key`.

Навыки по умолчанию сохраняются. `--mastery 0.2` явно задаёт 20% существующим навыкам; новые навыки не добавляются. Для старого снимка без контекста пересчёта такой override отклоняется, чтобы не оставить устаревшие производные бонусы. Живые стартовые слепки остаются Т0; `--player-tier` не превращает их в комплект другого тира.

## Управление прогоном

- `--feints both|none|player|monsters`: у обеих сторон, ни у кого, только у игрока или только у монстров.
- `--max-rounds 100`: ограничение длительности боя; ничьи учитываются отдельно.
- `--workers 2`: независимые сценарии в отдельных процессах. Это ускорение симуляций, а не нагрузочный тест сервера.
- `--output PATH`: новая либо пустая директория; существующий отчёт не перезаписывается.

## Артефакты и повторение

В каталоге результата: `report.html`, `summary.csv`, `summary.json`, `manifest.json` и подробные данные по сценариям. Сохраняются входные слепки, составы, исходы каждого seed, версия математики и отпечаток исходников. Отказ собрать отряд не считается проигранным боем.

```powershell
.venv/Scripts/python.exe -m tools.monsters.balance_probe --replay var/balance-probe/goblin-starter-easy/manifest.json --output var/balance-probe/goblin-starter-easy-replay
```

При изменении исходников повтор отклоняется. `--allow-source-drift` явно разрешает проверить сохранённые слепки новой версией кода; это уже не точное воспроизведение прежнего окружения.

Это постоянный инструмент. Недавние временные скрипты отдельных прогонов удалялись после сохранения результатов. Старые отчёты и специализированные постоянные инструменты `tools/monsters` сохраняются; массового удаления исторических файлов нет.

## Матрица всех стартовых билдов и полных комплектов Т0–Т4

```powershell
.venv/Scripts/python.exe -m tools.monsters.balance_probe.suite --battles 50 --workers 2 --output var/starter-full-t0-t4-easy
```

Сначала все четырнадцать настоящих стартовых слепков проверяются на Т0, затем их полные боевые комплекты на каждом тире Т0–Т4: обычная встреча, патруль, охрана, главарь, лёгкая сложность, финты у обеих сторон. Это 336 сценариев, по 50 попыток, всего 16 800 заказов; отказы сборки не выдаются за бои.

Сохраняются родные атрибуты, навыки и симбиот. Это намеренное сравнение экипировки, а не симуляция полностью прокачанного персонажа высокого тира. GS влияет на фактический состав противников. Все предметы создаются существующей фабрикой, со средними роллами и полезными легальными аффиксами; полезные сохраняются по цепочке. Целевые количества — 0/1/2/3/4, но более узкий полезный пул слота явно снижает фактическую редкость. Т4 уже допускает четыре аффикса.

`equipment.html` показывает предметы, `report.html` — сводную таблицу, каждая серия содержит собственные manifest, подробные составы и исходы. Для короткой проверки можно указать `--players starter_dual_blades_01 --tiers 0 --battles 1`.

## Тестовые распределения атрибутов

```powershell
.venv/Scripts/python.exe -m tools.monsters.balance_probe.attribute_trials --battles 50 --workers 4 --output var/starter-attributes-135-t0
```

Только аналитические варианты: текущие рабочие старты 135, равномерный контроль 135 и кандидаты из `attribute_profiles.py` на 135 очков с разрывом ≤8. Рабочие слепки не меняются. Предметы, навыки, симбиот и loadout сохраняются; raw пересобирается стандартным CharacterCombatMathModelBuilder.

Сначала каждый вариант сравнивается на четырёх одинаковых фиксированных тройках гоблинов Т0 с seed 0–49. Это контрольные примеры лёгких встреч, не вся библиотека составов. Затем подобранные кандидаты проверяются через настоящие четыре профиля easy; новый GS там влияет на состав. На этом этапе сравнение с фиксированным контролем не изолирует только влияние атрибутов.

Кандидаты обоснованы действующими формулами, но не являются доказанными глобальными оптимумами. Текущие распределения берутся из production starting_imprints, а не из исторического списка кандидатов. Равномерные 15 могут уступать старому распределению, несмотря на больший общий бюджет. Отчёт `index.html` сохраняет все варианты и результаты, а не скрывает неудачные.


## Принятая матрица альфы — пять семей

```powershell
.venv/Scripts/python.exe -m tools.monsters.balance_probe.alpha --battles 10 --workers 4 --output var/alpha-current
```

Один переносимый сценарий `alpha-heavy-guard-v1`: полный тяжёлый щитовик Т0–Т5, четыре типа встречи, три сложности, финты обеих сторон. Крысы/гоблины с Т0, волки/бандиты с Т1, големы с Т2. Это 26 сочетаний семья/тир, 312 сценариев и 3120 попыток при 10 боях. `--families golem_foundry --tiers 2 3` ограничивает выборку; `--seed`, `--battles`, `--workers` настраиваются. `--dry-run` проверяет входы и сохраняет план без боёв. Выходной каталог должен быть новым или пустым.

Игроки сохранены в отслеживаемом `data/alpha/heavy_guard_players.json`, поэтому `var` не нужен для запуска. Это точные исторические raw/loadout/items/skills, не автоматически оптимизированные новые комплекты: Т0 родные навыки, далее .1429/.2857/.4286/.5714/.7143, анатомия ≤.5, без добавленных бонусов симбиота. Текущий GS и waterfall пересчитываются стандартным валидатором. Новые результаты сравнивают сохранённого игрока с текущими Monsters и Combat; это не точное воспроизведение старого исходного кода. Для точного replay отдельного нового прогона применяется обычный manifest/replay.

Статические `accepted_settings.json` и `accepted_evidence.json` — обзор принятого состояния и исторические скалярные результаты всех пяти семей, не runtime-настройки и не тестовые гарантии побед. В `provenance.json` записаны происхождение и checksum входов. Исторические fingerprints намеренно не обновляются после изменения инструментов. Сырые логи и HTML остаются локально в `var`; переносимые данные от них не зависят. Подробности: `docs/ru/backend/features/monsters/alpha_acceptance.md`.
