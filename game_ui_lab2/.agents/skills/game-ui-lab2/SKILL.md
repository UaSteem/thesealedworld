# Игровой клиент: Lab2

Это активный самостоятельный прототип будущего игрового frontend, не Python/Jinja-приложение и не новый сайт. Старую game_ui_lab используем только как визуальный образец; не открывай её runtime-файлы как владельцев новой реализации.

## Начало работы

1. Прочитай [текущие решения](../../../docs/current-decisions.md), найди компонент по [карте файлов](../../../docs/file-map.md).
2. Прочитай нужный код и конкретное поручение. До правки кратко назови экран/файлы/границу. При потере контекста перечитай источники, не создавай новый интерфейс по памяти.
3. Выполняй узкую правку существующего компонента. Явное поручение владельца или работающего с Lab художника разрешает соответствующее изменение оформления; предложения и диагностические выводы сами по себе этого не разрешают. [Статус миграции](../../../docs/migration-status.md) — история реализации/проверок, а не приёмка владельцем.

## Владельцы и стек

- Vue 3 + JavaScript: HUD, окна, вкладки, формы, сообщения, навигация. Vite: dev/build. Phaser 3: игровое поле, камера, спрайты, анимации; один Game/canvas за src/engine/createField.js. Не добавлять TypeScript или Python. Не внедрять прежний boot.js/Jinja/DOM-контроллеры параллельно Vue.
- Рабочая папка — game_ui_lab2, включая ЕЁ src/. Корневой ../src (основная игра), ../game_ui_lab и ../rift_lab без отдельного поручения не менять. Наличие общей папки src в имени не делает backend доступным клиенту.
- App.vue только компонует. Представление → сценарий/gateway → adapter. Компонент не знает способ получения данных; adapter подменяется моковым. Никаких backend imports, БД, генераторов, resolver, копий игровых расчётов. Готовые mock ответы допустимы, моделировать второй движок нельзя.
- Чат и боевой журнал — разные источники/подписки/хранилища; вместе только оболочка вкладок. Вкладка Бой доступна только в combat и не имеет ввода. При выходе/деактивации отписываться от потока. Камера/Phaser не пересоздаются при каждом окне.
- Lifecycle обязателен: очищать слушатели, таймеры, observers и Phaser Game; для KeepAlive учитывать activate/deactivate. Не измерять скрытые DOM-узлы. Перерасчёт сетки не должен менять ширину своего измеряемого viewport через появление скролла.

## Данные и интерфейс

Основа следующей задачи — последняя согласованная версия и существующие изменения в рабочих файлах. PR4 и исходный вид миграции — начальная точка, не шаблон для восстановления. Вне порученной правки сохранять текущую композицию, палитру, максимум1920 и игровые переходы/возвраты; Debug их не заменяет. Будущая переработка боя — отдельное поручение. Никакого редизайна заодно.

Порученные изменения шрифтов, цветов и геометрии не отменять на следующей задаче из-за старого описания. После изменения принятого решения обновить соответствующий пункт current-decisions.md: что изменено, по чьему поручению, что проверено и что ещё не принято. Не объявлять выполнение приёмкой, но и не откатывать выполненную работу из-за отсутствия отдельной приёмки. При новом чате сначала сверить решения и diff. Если текущие файлы и заметки расходятся, не восстанавливать старый вид автоматически: сохранить правки и выяснить источник расхождения. Сохранение текущего результата не требует дополнительного согласования каждой мелкой правки.

Поле в DTO не автоматически пользовательская характеристика. Для модификаторов проверять реальные потребители и единицы в текущем backend; 145 полей общей схемы не являются утверждёнными145 модификаторами игрока. Боевые предметы item_*, промежуточные расчёты, временно отключённые механики и мирные показатели различать; см. текущие решения. Не смешивать модификаторы с бафами. Полноту каталога не доказывать малой выборкой, но и не подменять player projection выгрузкой DTO.

Атака показывает итоговые урон/точность/крит только имеющегося оружия по рукам; щит относится к Защите. Общие прямые бонусы отдельно. Использовать явную карту player-modifier-layout.json; внутренние коэффициенты/raw/mastery/caps не выводить. Готовые профили атак поступают из gateway, формулы backend в UI не копировать.

Fixture-форматы предварительные: не объявлять их реальным API. Недостающие данные/действия отмечать как требования к backend; не выдумывать их поддержку и не исправлять серверную формулу в браузере.

## Ассеты и границы миграции

В public только используемые материалы/manifest. Новые пробы держать в experiments/visuals/<задача>/ вне active assets, мастера в sources/. Не скрывать дефект ассета новым объектом/обходом без обсуждения. Не менять выбранные размеры/пропорции без задания; crop сверять с фактической текстурой.

Старая Lab пока не удаляется и Lab2 не переименовывается. Будущие замена папок, перенос в корневой src/game_client и удаление заменённой игровой части src/frontend — отдельные этапы после проверки. Не создавать вторую независимую копию клиента для Rift Lab. Runtime и dist не должны зависеть от соседней Lab или абсолютных путей компьютера.

## Проверка

Команды — в [README](../../../README.md): pnpm dev (8880), pnpm test, pnpm build, pnpm preview (8881). Python/старый порт8879 не нужны для работы Lab2. dist/node_modules не коммитить.

После правки открыть актуальный экран, проверить ввод/выбор/закрытие/возврат/ограничения и ближайший переход. Для геометрии проверить1366×768,1920×1080 и верхний предел ширины. Для gateways — ошибки и отписки; для переноса — собранный dist и наличие ассетов. Сборка/покрытие схемы не доказывают визуальную приёмку или работоспособность механик. Кратко сообщать фактические проверки и пробелы. Коммит/push только по поручению. Независимый ревизор — по выбранному режиму задачи.
